# Flux Web

Public website for **Flux** — a real-time messaging app. Built with the Next.js
App Router, TypeScript, and Tailwind CSS.

This is the web front end only. The backend lives in `../backend/` and the
Flutter app in `../mobile/`; neither is modified here.

## What is implemented

- Marketing landing page at `/` — includes an interactive chat-showcase demo
  (auto-playing simulated conversations plus an in-page contact search)
- Password-reset page at `/reset-password?token=…`
- Email-verification page at `/verify?token=…`
- Informational placeholders for `/docs`, `/privacy`, `/terms`

The reset and verify pages are functional clients for the existing backend
endpoints. They do not persist tokens, add analytics, or sign users in after a
reset. Both flows are E2E-proven against the real backend — report in
`../docs/web-task-04.md`.

## Getting started

The backend must be running for the reset and verify pages to work.

```bash
# Terminal 1 — backend (http://localhost:3000)
cd ../backend
npm run dev

# Terminal 2 — web (http://localhost:5173)
cd web
npm install
npm run dev -- -p 5173
```

Why 5173? The backend's current development `FRONTEND_URL` is
`http://localhost:5173`, so reset and verification links generated by local
emails point there. `npm run dev` alone starts Next on 3000 and conflicts with
the backend.

Copy `.env.example` to `.env.local` if you need to override defaults:

```bash
cp .env.example .env.local
```

| Variable                    | Purpose                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------ |
| `NEXT_PUBLIC_SITE_URL`      | Origin used for metadata/Open Graph URLs                                                         |
| `NEXT_PUBLIC_API_BASE_URL`  | Origin of the Flux backend API (required in production; dev falls back to `http://localhost:3000`) |

`NEXT_PUBLIC_*` values are inlined at build time. Set them in the Vercel
project before running the production build.

## Security notes

- Tokens are read from the URL in the browser and never written to
  `localStorage`, `sessionStorage`, cookies, or logs.
- Opening a reset link calls the backend's non-consuming validation endpoint.
  Opening a verification link makes no request until the user submits.
- Both token pages send `noindex`/`no-referrer` metadata and headers, and
  `Cache-Control: no-store`.
- The API client sends `credentials: "omit"` and never hardcodes a production
  hostname.
- The reset form mirrors the backend password policy (8–128 chars, upper,
  lower, digit). The backend remains authoritative.

## Deployment

At minimum:

1. Set `NEXT_PUBLIC_API_BASE_URL` to the production API origin and
   `NEXT_PUBLIC_SITE_URL` to the deployed web origin in Vercel — both bake in
   at build time, so redeploy after any change.
2. Add the web origin to the backend's `CORS_ORIGINS` and deploy the backend
   with real email credentials (checklist: `../docs/web-task-04.md` §13; the
   backend's planned home is a single Oracle Cloud VPS — runbook at
   `../execution/20-deployment/phase-01-backend-deploy/vps-oracle.md`).
3. Deploy a preview; test `verify` and `reset-password` with fresh signups
   end-to-end on the deployed pair.
4. Only then switch the backend's production `FRONTEND_URL` /
   `VERIFICATION_URL` to this app. The static pages in `../vercel-pages/`
   remain the rollback path.

## Brand

Colors and typography mirror `../mobile/lib/app/colors.dart` and the mobile
theme. Fonts (`Urbanist`, `PlusJakartaSans`) are bundled locally from the
Flutter app's assets, so no external font network is required at build time.
